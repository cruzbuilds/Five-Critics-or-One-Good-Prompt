# Pre-production review of Idea Log (Next.js 16 / Prisma / Postgres)

I found no critical issues. There are 2 high, 9 medium, 12 low and 5 informational findings. The core ownership scoping is consistent: every idea query filters by `userId`, and the share endpoints only ever look up by token.

**What I could not do:**
- `node_modules` isn't installed, so I did not run `next build`, `tsc`, `eslint` or `pnpm audit`.
- I could not read the Next 16 docs in `node_modules/next/dist/docs/` that `AGENTS.md` asks for. Findings about Next-specific behavior come from the source only.
- I did not check the pinned versions (`next@16.3.5`, `nanoid@6.0.1`, `zod@4.6.5`) against advisories, so the dependency audit is still open.

---

## High

**1. The placeholder `JWT_SECRET` passes validation and the README says to keep it**
- **Where:** `.env.example:2`, `src/lib/auth.ts:9`, `README.md:27`
- **Problem:** The only check is `secret.length < 16`, and the placeholder `change-me-to-a-long-random-string` is 33 characters. The README says to "keep the defaults".
- **Failure:** A deployment that copies `.env.example`, which is the documented path, signs sessions with a publicly known key. Anyone can mint an HS256 token with `sub` set to a victim's user id and get full access to that account. The attacker needs a valid id; Prisma `cuid()` ids are not secret, but guessing one is nontrivial. That is why this is High rather than Critical.
- **Fix:**
  - Reject known placeholders and require at least 32 bytes of entropy.
  - Change the README to say `openssl rand -base64 48`.
  - Ship no usable default in `.env.example`, for example an empty value.

**2. No rate limiting or lockout on login and register, and hashing is CPU-heavy**
- **Where:** `src/app/api/auth/login/route.ts:7`, `src/app/api/auth/register/route.ts:7`, `src/lib/auth.ts:21`
- **Problem:** Nothing throttles by IP or account. The minimum password is 8 characters with no other rules. Hashing uses pure-JS `bcryptjs` at cost 12, and it runs on the single Node thread.
- **Failure:**
  - An attacker can run unlimited password guessing against a known email.
  - A flood of `POST /api/auth/register` or `/login` requests with 200-character passwords saturates the CPU and stalls the whole app, including the public share pages. Login for unknown emails skips bcrypt, so the cost difference also helps the attacker.
- **Fix:**
  - Add per-IP and per-account rate limiting and progressive lockout, at the edge or in a store such as Redis.
  - Use native `bcrypt` or argon2 so hashing runs off the event loop.
  - Consider CAPTCHA or email verification on register.

## Medium

**3. A missing or short `JWT_SECRET` fails late, and register leaves a half-created account**
- **Where:** `src/lib/auth.ts:7-13`, `src/app/api/auth/register/route.ts:28-32`, `src/proxy.ts:11`
- **Problem:** The secret is validated lazily, on first sign or verify, not at startup. Register creates the user row first and calls `setSessionCookie` afterwards.
- **Failure:** With the secret unset or too short:
  - Registration returns 500 but the user row already exists. A retry returns 409 "already exists", and login also returns 500.
  - `proxy.ts` swallows the throw in `verifySessionToken`'s catch and redirects every `/ideas` request to `/login`, so the failure looks like an auth problem, not a config problem.
- **Fix:**
  - Validate all env vars once at boot (Zod env module, `instrumentation.ts`) and fail fast.
  - Sign the session before writing the user, or catch and roll back.

**4. Sessions can't be revoked, and there is no password reset, password change or email verification**
- **Where:** `src/lib/auth.ts:31-38`, `src/lib/session.ts:24-27`, `src/app/api/auth/register/route.ts`
- **Problem:** Sessions are stateless 30-day JWTs, and logout only deletes the browser cookie. No account-recovery or email-confirmation flow exists.
- **Failure:**
  - A stolen cookie stays valid for up to 30 days, even after logout.
  - Anyone can register with someone else's email, which locks out the real owner.
  - A forgotten password means permanent lockout.
- **Fix:**
  - Add a `sessionVersion` or session table, checked in `getCurrentUser`, so logout and password change can invalidate sessions.
  - Add email verification and a reset flow.
  - Shorten the TTL or add refresh.

**5. Account enumeration through the register error and login timing**
- **Where:** `src/app/api/auth/register/route.ts:19-25`, `src/app/api/auth/login/route.ts:19-22`
- **Problem:** Register returns a distinct 409 for existing emails. Login returns immediately for unknown emails but runs a ~250 ms bcrypt compare for known ones.
- **Failure:** An attacker can enumerate registered emails and then target them with the guessing from #2.
- **Fix:** Use a generic register response with email confirmation. Always run a dummy `bcrypt.compare` against a fixed hash when the user is not found.

**6. Predictions can be edited after the outcome is recorded, which undermines calibration**
- **Where:** `src/app/api/ideas/[id]/route.ts:37-40`, `src/lib/validation.ts:30-38`
- **Problem:** The whole purpose of the app is comparing the original prediction with hindsight. `PATCH /api/ideas/[id]` accepts new `differentiation`, `evidence`, `cost` and `reversibility` values at any time.
- **Failure:** After recording an outcome, a user can rewrite the predictions so the delta and the dashboard calibration numbers look accurate.
- **Fix:** Reject prediction-score edits once `outcomeRecordedAt` is set, or store the predictions as an immutable snapshot. This is a product decision, so confirm the intended behavior.

**7. `status` and outcome data can become inconsistent**
- **Where:** `src/lib/validation.ts:33`, `src/app/api/ideas/[id]/route.ts:37`, `prisma/schema.prisma:33-47`
- **Problem:** The generic PATCH lets a client set `status` without touching `outcome` or the hindsight scores, and the database has no constraint tying them together.
- **Failure:**
  - `PATCH {status:"DONE"}` produces a DONE idea with no outcome.
  - `PATCH {status:"ACTIVE"}` on a finished idea leaves the outcome and hindsight scores in place. The calibration summary counts it (`calibration.ts:15` filters on `hindsightTotal`, not status), and the shared page still shows the outcome.
- **Fix:** Remove `status` from `ideaUpdateSchema` and route it through the outcome endpoint. Add a DB CHECK such as `(status='ACTIVE') = (outcome IS NULL)`, plus all-or-none on the four `h*` columns.

**8. Registration race returns a 500**
- **Where:** `src/app/api/auth/register/route.ts:19-30`
- **Problem:** The code does `findUnique` and then `create` with no handling of the unique-constraint violation.
- **Failure:** Two concurrent registrations for the same email both pass the check, and one gets an unhandled Prisma `P2002` and a 500.
- **Fix:** Drop the pre-check, catch `P2002` around `create`, and return the same generic response.

**9. There is no production migration path**
- **Where:** `package.json:12`, `README.md:26-30`, `README.md:64-65`
- **Problem:** The only migration script is `prisma migrate dev`. There is no `prisma migrate deploy` script, and the README says nothing about how to apply migrations in production.
- **Failure:** An operator following the README runs `migrate dev` against a production database. That command is interactive and can prompt to reset the schema, which would delete data.
- **Fix:** Add a `db:deploy` script running `prisma migrate deploy`. Document the deploy sequence (`generate`, `migrate deploy`, `build`, `start`) and a backup step.

**10. There are no tests**
- **Where:** `package.json` has no test script or test dependency, and no test files exist.
- **Failure:** Nothing checks the security-critical behavior: ownership scoping (IDOR), share-token issue/rotate/revoke, unauthenticated access to `/api/ideas*`, the score-range rules, or the scoring and calibration math. A regression ships silently.
- **Fix:** Add integration tests (Vitest or Jest plus a test Postgres) that cover at minimum:
  - user A cannot read, patch, delete or share user B's idea;
  - a revoked or rotated token returns 404;
  - the validation boundaries;
  - the scoring and calibration unit tests.

**11. There is no deployment or CI configuration**
- **Where:** repository root
- **Problem:** The repo has no Dockerfile, CI workflow, health-check endpoint, structured logging or error monitoring. The single commit message is "raw generated build, unreviewed".
- **Failure:** No automated `lint` or `tsc` gate exists, no readiness probe is available for an orchestrator, and production failures are invisible. Next 16's default route-error handling only logs to stdout.
- **Fix:** Add a CI pipeline (`pnpm install --frozen-lockfile`, lint, typecheck, test, build). Add a container or platform config, a `/api/health` route that checks the DB, and log/error reporting.

## Low

**12. The docker-compose Postgres is exposed on all interfaces with default credentials**
- **Where:** `docker-compose.yml:5-10`
- **Problem:** The credentials are `idealog/idealog` and the port mapping `"5432:5432"` binds to 0.0.0.0.
- **Failure:** If this file is used on any shared or internet-reachable host, anyone can connect to the database. The README frames it as local-only, so this is Low unless it is reused.
- **Fix:** Bind to loopback (`127.0.0.1:5432:5432`), read credentials from env, and state "dev only" in the file.

**13. No security headers are configured**
- **Where:** `next.config.ts:3-5`
- **Problem:** There is no CSP, HSTS, `X-Content-Type-Options`, `Referrer-Policy` or `frame-ancestors`.
- **Failure:** The app can be framed and has no defense-in-depth against future XSS. `SameSite=Lax` partly blunts clickjacking of the delete and share buttons.
- **Fix:** Add a `headers()` block in `next.config.ts`.

**14. The auth JSON endpoints have no CSRF or Content-Type guard, so login CSRF is possible**
- **Where:** `src/app/api/auth/login/route.ts:8`, and the same pattern in every POST/PATCH/DELETE route
- **Problem:** `req.json()` parses any Content-Type, and no `Origin` check exists. `SameSite=Lax` covers cookie-carrying requests.
- **Failure:** A cross-site `text/plain` form post to `/api/auth/login` needs no cookie. It logs the victim into an attacker's account, and the victim's ideas end up stored there. This needs the attacker's credentials to be useful.
- **Fix:** Require `Content-Type: application/json` and verify `Origin` or `Sec-Fetch-Site` for mutating routes.

**15. `jwtVerify` does not pin the algorithm**
- **Where:** `src/lib/auth.ts:44`
- **Problem:** No `algorithms: ["HS256"]` option is passed. A symmetric `Uint8Array` key already limits this to HS*, so it is a hardening gap, not an exploit.
- **Fix:** Pass `{ algorithms: ["HS256"] }`.

**16. bcrypt silently truncates passwords beyond 72 bytes, and the password policy is weak**
- **Where:** `src/lib/validation.ts:6`, `src/lib/auth.ts:21`
- **Problem:** The schema allows 200 characters, but bcrypt ignores everything past byte 72. The only rule is a minimum of 8 characters.
- **Failure:** Two different long passwords with the same 72-byte prefix are treated as identical.
- **Fix:** Cap at 72 bytes, or pre-hash or switch to argon2. Consider a breached-password check.

**17. Public shared pages have no `noindex`, no referrer policy and no cache headers**
- **Where:** `src/app/s/[token]/page.tsx:12-22`
- **Problem:** The token is the only protection. There is no `robots: {index:false}` and no `Referrer-Policy`.
- **Failure:** If a link is pasted somewhere crawlable, the private idea is indexed. Rendering also queries the DB twice per view, once in `generateMetadata` and once in the page (lines 18 and 30).
- **Fix:** Add `robots: noindex, nofollow` and `referrer: no-referrer` metadata. Wrap `getSharedIdea` in React `cache()`.

**18. Two unused API routes duplicate logic and widen the public surface**
- **Where:** `src/app/api/share/[token]/route.ts:9`, `src/app/api/auth/me/route.ts:4`
- **Problem:** Nothing in `src` calls either route. The share route re-implements the public serialization that `s/[token]/page.tsx` does inline (already slightly different, `delta` versus `hTotal - total`), and it is unauthenticated.
- **Fix:** Delete them, or share one serializer between the page and the API.

**19. Client-side hydration mismatches**
- **Where:** `src/components/share-control.tsx:18-23`, `src/components/idea-detail.tsx:189`
- **Problem:**
  - `ShareControl` branches on `typeof window` during render, so the server renders `/s/<token>` and the client renders the full origin.
  - `toLocaleDateString()` runs in a component that is server-rendered and then hydrated, so the server and client locale or timezone can differ.
- **Failure:** React hydration warnings, and possibly a flash of a wrong value. I have not run it to confirm.
- **Fix:** Compute the origin in an effect, and format dates with a fixed locale and timezone, or only on the client.

**20. Client `fetch` calls have no network-failure handling**
- **Where:** `src/components/auth-form.tsx:26`, `idea-create-form.tsx:40`, `outcome-form.tsx:44`, `idea-detail.tsx:57` and `:75`, `share-control.tsx:27` and `:40`
- **Problem:** There is no `try/catch`. Share and delete errors are also silently swallowed on a non-OK response.
- **Failure:** On a dropped connection the promise rejects and `loading` stays true. The submit button reads "Please wait…" forever and the user must reload. A failed delete or revoke shows no message, so a user may believe a link was revoked when it was not.
- **Fix:** Wrap in `try/finally` and surface errors.

**21. Ownership is checked in a separate read, and writes then use the id alone**
- **Where:** `src/app/api/ideas/[id]/route.ts:25-40` and `:50-53`, `.../outcome/route.ts:14-26`, `.../share/route.ts:15-27` and `:38-44`
- **Problem:** The routes call `findFirst({id,userId})` and then `update({where:{id}})`.
- **Failure:** There is no exploitable IDOR today, because ids and owners are immutable. A concurrent delete makes `update` or `delete` throw `P2025`, which is an unhandled 500. A future refactor that drops the pre-check would become an IDOR.
- **Fix:** Use `updateMany` or `deleteMany` with `{id, userId}` and return 404 when the count is 0.

**22. Users and ideas are unbounded**
- **Where:** `src/app/api/ideas/route.ts:15-21`, `src/app/ideas/page.tsx:12`, `src/app/api/ideas/route.ts:43`
- **Problem:** The list has no pagination or limit and is sorted in JS. There is no per-user idea quota and no request-body size limit. Each idea can hold about 10 KB of text, and there is no email verification to limit signups.
- **Failure:** An account can fill the database. A heavy account makes the dashboard slow and large.
- **Fix:** Add pagination or a cap, a quota, and a body-size check.

**23. Validation errors are returned raw and are unhelpful**
- **Where:** `issues[0]?.message` in `login/route.ts:12`, `register/route.ts:12`, `ideas/route.ts:38`, `ideas/[id]/route.ts:32`, `outcome/route.ts:21`
- **Problem:** Zod 4 messages omit the field name, for example "Too small: expected string to have >=8 characters". The form inputs also carry no `maxLength` attributes. `GET /api/ideas?status=bogus` is silently ignored and returns all ideas (`ideas/route.ts:13`).
- **Fix:** Return `{field, message}` and 400 on an invalid `status`.

## Informational

**24. README inaccuracies and gaps**
- **Where:** `README.md:10`, `README.md:9`, `README.md:23`
- **Problem:**
  - "unshareable/unguessable link" should be "unlisted".
  - It says `bcrypt`, but the code uses `bcryptjs`.
  - "Node 20+" is probably 20.9+ for Next 16, which I could not confirm.
  - The README documents no production deployment, no secret generation, no required env vars beyond the two listed, and no backup or restore procedure.
  - It does not say that `prisma/migrations/20260917213700_score_checks` holds CHECK constraints that exist nowhere in `schema.prisma`.

**25. Database design notes**
- **Where:** `prisma/schema.prisma:19` and `:55`, `prisma/migrations/20260917213700_score_checks/migration.sql`
- **Notes:**
  - Email uniqueness is case-sensitive in the DB. It only works because the app lowercases, so any second write path would break it.
  - `@@index([userId])` is redundant with `@@index([userId, status])`.
  - Text lengths are enforced only in Zod.
  - The CHECKs live only in raw SQL, so `prisma db push` or a schema-only workflow would not recreate them.
- **Fix:** Use a `citext` column or a lower(email) unique index, drop the redundant index, and add a note about the CHECKs to the schema.

**26. Dependency and build notes**
- **Where:** `package.json:16` and `:21`, `src/app/layout.tsx:2`
- **Notes:**
  - `@prisma/client` is `^6.19.3` while `prisma` is exact `6.19.3`. A re-resolve can produce a client/CLI version skew; the lockfile prevents it today.
  - `next/font/google` fetches fonts at build time, so an offline or air-gapped CI build fails.
  - Audit still to do: run `pnpm audit` after install.

**27. Small design leftovers**
- **Where:** `src/lib/types.ts:4`, `src/proxy.ts:15`, `src/lib/auth.ts:33`
- **Notes:**
  - `serializeIdea` sends `userId` to the client, which is not needed.
  - The redirect to `/login` drops the original URL, so there is no return-to.
  - The JWT carries `email`, which nothing reads and which would go stale.

**28. Missing product and compliance features**
- **Notes:**
  - There is no account or data deletion, and no data export. Deletion is a GDPR-type expectation, though the schema's `onDelete: Cascade` would make it easy to add.
  - No terms or privacy policy.
  - No custom `error.tsx`, `not-found.tsx` or `loading.tsx`.
