## High

### 1. The documented default `JWT_SECRET` is accepted, so session cookies can be forged
- **Severity:** high (when the placeholder is used)
- **Where:** `.env.example:2`, `README.md:27`, `src/lib/auth.ts:9`
- **What's wrong:** The only secret check is `length >= 16`. The placeholder `change-me-to-a-long-random-string` is 33 characters, so it passes. The README says to fill it in "or keep the defaults".
- **Failure:** If production is configured from `.env.example`, anyone can sign an HS256 JWT with the public secret and a chosen `sub`. `getCurrentUser` only looks up `sub`, and the `email` claim is never compared to the database. The attacker needs a valid user id, which is a cuid. cuids are not enumerable, but they are not secret either. This is a full account takeover for any known id.
- **Fix:**
  - Reject known placeholders and require at least 32 bytes of entropy.
  - Validate env vars once at startup (a `zod` env module) so the process fails to boot.
  - Remove "keep the defaults" from the README.
  - Ship no usable secret in `.env.example` (leave it blank, with a `openssl rand -base64 48` hint).

### 2. No rate limiting, and password hashing is pure-JS bcrypt at cost 12
- **Severity:** high
- **Where:** `src/app/api/auth/login/route.ts:7`, `src/app/api/auth/register/route.ts:7`, `src/lib/auth.ts:21`
- **What's wrong:** No throttling, lockout or CAPTCHA exists on login or register. `bcryptjs` runs on the Node main thread.
- **Failure:**
  - Credential stuffing and password guessing against `/api/auth/login` are unlimited.
  - Bulk fake signups are unlimited, and email verification is missing (see finding 6).
  - Each `bcrypt.hash(…, 12)` or `compare` costs a few hundred ms of pure-JS CPU. A modest number of concurrent requests saturates the process and takes the whole app down (a CPU DoS).
- **Fix:**
  - Add per-IP and per-account rate limits, at the edge or with a shared store such as Redis.
  - Add progressive backoff on login failures.
  - Use native `bcrypt`, or `argon2` or Node `crypto.scrypt`, so hashing runs off the event loop.

## Medium

### 3. `nanoid@6` needs Node 22+, but the README, types and `package.json` target Node 20
- **Severity:** medium (needs confirming)
- **Where:** `package.json:19`, `pnpm-lock.yaml:1711` (`engines: node ^22 || ^24 || >=26`), `README.md:23`, `@types/node ^20`
- **What's wrong:** The dependency's engine range excludes Node 20, which the README says is supported. `package.json` has no `engines` field or `.nvmrc`. Node 20 is also past end of life as of today (2026-09-18).
- **Failure:** On Node 20, pnpm only warns at install. The share-link route (`src/app/api/ideas/[id]/share/route.ts:22`) may then fail at build or runtime. I couldn't run it to confirm.
- **Fix:**
  - Set `engines.node` to `>=22` and add `.nvmrc`.
  - Update the README and `@types/node`.
  - Or drop `nanoid` for `crypto.randomBytes(18).toString("base64url")`.

### 4. User enumeration on register and login
- **Severity:** medium
- **Where:** `src/app/api/auth/register/route.ts:19-25`, `src/app/api/auth/login/route.ts:19-22`
- **What's wrong:**
  - Register returns a distinct `409 "An account with that email already exists"`.
  - Login returns immediately when the user isn't found, but runs a ~250 ms bcrypt compare when the user exists.
- **Failure:** An attacker can enumerate registered emails, from the 409 or by timing the login response. Combined with finding 2, that gives a target list for credential stuffing.
- **Fix:**
  - Always run a dummy `bcrypt.compare` against a fixed hash when the user isn't found.
  - On register, use a generic response, or email-verify and reply "check your inbox" either way.

### 5. Predictions can be edited after hindsight is recorded, which defeats the calibration feature
- **Severity:** medium
- **Where:** `src/app/api/ideas/[id]/route.ts:37-40`, `src/lib/validation.ts:30-38`, `src/components/idea-detail.tsx:120`
- **What's wrong:** `PATCH /api/ideas/[id]` and the always-visible Edit button let the four prediction scores be changed at any time, including after an outcome exists. The schema comment says they are "recorded when the idea is logged".
- **Failure:** A user finishes an idea, sees they were wrong, and edits the original scores. The calibration averages (`src/lib/calibration.ts`) then measure nothing, and there is no audit trail.
- **Fix:**
  - Reject prediction-score changes once `outcomeRecordedAt` is set, and ideally lock them after a grace period.
  - Or store prediction history as versioned rows.

### 6. No password reset, password change, email verification, session revocation or account deletion
- **Severity:** medium
- **Where:** `src/lib/auth.ts:5,31-38`, `src/lib/session.ts:24-27`, no such routes exist
- **What's wrong:**
  - Sessions are stateless 30-day JWTs with no version or jti. "Logout" only deletes the cookie in the browser.
  - There is no way to change or reset a password, and no email ownership check.
  - There is no way for a user to delete their account, although the schema cascades.
- **Failure:**
  - A user who forgets their password is locked out permanently.
  - A stolen cookie stays valid for 30 days even after logout.
  - Anyone can register someone else's email and squat it.
  - There is no route for account or data deletion, which privacy law may require.
- **Fix:**
  - Add a `sessionVersion` or session table and check it in `getCurrentUser`.
  - Add reset and change-password flows, with email verification.
  - Add account deletion and export.

### 7. No security headers
- **Severity:** medium
- **Where:** `next.config.ts:3`
- **What's wrong:** The config is empty. There is no CSP, `X-Frame-Options` or `frame-ancestors`, HSTS, `Referrer-Policy`, `X-Content-Type-Options` or `Permissions-Policy`.
- **Failure:**
  - The authenticated UI can be framed and clickjacked.
  - There is no CSP backstop for a future injection bug.
  - HSTS is missing unless the reverse proxy sets it, and nothing documents that it must.
- **Fix:** Add an async `headers()` block in `next.config.ts` (or set them in the proxy) with these headers.

### 8. Unbounded queries, request bodies and per-user data
- **Severity:** medium
- **Where:** `src/app/api/ideas/route.ts:15-21`, `src/app/ideas/page.tsx:12-15`, all `req.json()` calls
- **What's wrong:**
  - The list endpoint and dashboard load every idea for a user with no `take` or pagination.
  - Each description can be 5,000 characters, and there's no cap on idea count.
  - The API reads bodies with `req.json()` and no size limit before validation. `passwordSchema.max(200)` only applies after the whole body is parsed.
- **Failure:** One account can create thousands of ideas, so `/ideas` and `/api/ideas` return multi-megabyte payloads and slow the server. A very large JSON body is fully buffered before Zod rejects it.
- **Fix:**
  - Paginate or cap results, and cap ideas per user.
  - Check `Content-Length` and reject oversized bodies early.
  - Consider computing the sort in SQL.

### 9. `docker-compose.yml` exposes Postgres with default credentials on all interfaces
- **Severity:** medium (if used beyond a laptop)
- **Where:** `docker-compose.yml:5-10`
- **What's wrong:** The credentials are `idealog/idealog`, and `"5432:5432"` publishes the port on `0.0.0.0`.
- **Failure:** On a shared network or cloud VM, anyone who can reach port 5432 can log in and read every password hash. The README treats this as the only infrastructure config, so it is likely to be reused for a real deploy.
- **Fix:**
  - Bind to `127.0.0.1:5432:5432`.
  - Read credentials from env.
  - Label the file dev-only, and document a real production database setup with TLS (`sslmode=require`).

### 10. No tests, CI or type-check script
- **Severity:** medium
- **Where:** `package.json:5-13`, no test files or CI config anywhere
- **What's wrong:** There is no test runner, no `test` or `typecheck` script, and no CI. The commit is titled "raw generated build, unreviewed".
- **Failure:** The ownership check `findFirst({ id, userId })` is hand-copied across six handlers, and the auth gate, validation and scoring math (`src/lib/scoring.ts`, `calibration.ts`) have no regression protection. A cross-user read, or a status/score bug, ships silently.
- **Fix:**
  - Add unit tests for scoring and calibration, and API tests for auth and authorization (401, cross-user 404, invalid input, share and revoke).
  - Add CI running lint, `tsc --noEmit`, tests, `next build` and `pnpm audit`.

### 11. No deployment or production runbook
- **Severity:** medium
- **Where:** `package.json:12` (only `prisma migrate dev`), `README.md`
- **What's wrong:**
  - There is no Dockerfile, no `prisma migrate deploy` step, no health endpoint and no documented production env vars.
  - `secure` cookies depend on `NODE_ENV=production` (`src/lib/session.ts:17`), which the docs don't mention.
  - The proxy builds redirects from `req.url` (`src/proxy.ts:15`), which could carry an internal host behind a reverse proxy (unconfirmed).
  - The dev script `migrate dev` can prompt or reset data if pointed at the wrong DB.
- **Failure:**
  - Migrations, including the CHECK constraints migration, may never be applied in production.
  - Serving over plain HTTP silently drops the Secure cookie and breaks login.
  - There is no way for a load balancer to check the app.
- **Fix:** Document and script a `prisma migrate deploy` release step, add a `/api/health` route, and document TLS, env vars, reverse-proxy headers and backups.

## Low

### 12. Duplicate registration race returns a 500
- **Where:** `src/app/api/auth/register/route.ts:19-30`
- **What's wrong:** It does a check-then-insert with no handling of Prisma unique-violation `P2002`.
- **Failure:** Two concurrent requests with the same email both pass the `findUnique`. The second `create` throws, and the user gets an unhandled 500.
- **Fix:** Drop the pre-check, catch `P2002`, and return the response you choose for duplicates.

### 13. No error handling around database calls, and no error pages
- **Where:** all route handlers; no `error.tsx`, `global-error.tsx` or `not-found.tsx` under `src/app`
- **What's wrong:** Prisma calls aren't wrapped. There is no logging, monitoring or error boundary.
- **Failure:** A database outage or unexpected throw surfaces as an opaque 500 or the default error UI, with nothing recorded about auth failures or 5xx responses. Note that `not-found` still renders the default 404.
- **Fix:** Add a try/catch wrapper for handlers with structured logging, plus `error.tsx` and `not-found.tsx`.

### 14. `verifySessionToken` swallows secret misconfiguration
- **Where:** `src/lib/auth.ts:44-51`
- **What's wrong:** `getSecretKey()` throws inside the `try`, so a missing or short `JWT_SECRET` is treated as "invalid token".
- **Failure:** `/ideas` silently redirects to `/login` for everyone. Login itself then 500s (`createSessionToken` isn't guarded), so the cause is hard to find.
- **Fix:** Validate the secret at startup, and only catch verification errors.

### 15. JWT claims are minimal and loosely verified
- **Where:** `src/lib/auth.ts:31-47`
- **What's wrong:** There is no `iss` or `aud`, `algorithms` isn't pinned in `jwtVerify`, and `email` is embedded in the token and never revalidated.
- **Failure:** Low exposure today, because jose restricts HMAC keys to HS* algorithms. The risk is future drift: a stale email claim after any email change, or token reuse if a second service shares the secret.
- **Fix:** Pin `algorithms: ["HS256"]`, add issuer and audience, and drop `email` from the token.

### 16. `getCurrentUser` loads the full user row, including `passwordHash`
- **Where:** `src/lib/session.ts:40`
- **What's wrong:** `findUnique` has no `select`, and it runs for every page render through the layout header.
- **Failure:** Nothing leaks today. But any future code that passes `user` into a client component or JSON response would expose the hash.
- **Fix:** Select only `id`, `email` and `name`.

### 17. bcrypt 72-byte truncation
- **Where:** `src/lib/validation.ts:6`, `src/lib/auth.ts:21`
- **What's wrong:** Passwords up to 200 characters are accepted, but bcrypt only uses the first 72 bytes.
- **Failure:** Two long passwords with the same 72-byte prefix are equivalent. I couldn't confirm whether `bcryptjs@3.0.3` still truncates silently; check its README or test it.
- **Fix:** Cap the byte length at 72 (or pre-hash), or use argon2.

### 18. No CSRF or Origin defence beyond `SameSite=Lax`
- **Where:** all mutating route handlers, `src/lib/session.ts:18`
- **What's wrong:** Handlers call `req.json()` regardless of `Content-Type` and don't check `Origin`.
- **Failure:** Lax blocks classic cross-site POSTs. But same-site sibling origins (other subdomains) and login CSRF, where an attacker signs the victim into the attacker's account, are not covered.
- **Fix:** Require `Content-Type: application/json`, check `Origin` or `Sec-Fetch-Site`, and consider the `__Host-` cookie prefix.

### 19. Ideas can be left in inconsistent states
- **Where:** `src/lib/validation.ts:33`, `src/app/api/ideas/[id]/outcome/route.ts:31`, `prisma/schema.prisma:41-47`
- **What's wrong:**
  - `PATCH /api/ideas/[id]` accepts `status` on its own, so an idea can be `ACTIVE` while carrying an outcome and hindsight, or `DONE` with none.
  - `outcomeRecordedAt` is overwritten on every outcome edit, so "Recorded <date>" changes when text is fixed.
  - The database doesn't require hindsight scores to be all present or all null.
- **Failure:** Dashboards mislabel ideas, and the calibration set can include ideas the UI treats as unfinished.
- **Fix:** Drop `status` from the generic update schema, set `outcomeRecordedAt` only on first record, and add a CHECK for the all-or-nothing hindsight columns.

### 20. Hindsight forms don't show what the scales mean
- **Where:** `src/components/outcome-form.tsx:97-103`, `src/components/idea-detail.tsx:142-147`; the hints exist only in `src/components/idea-create-form.tsx:9-12`
- **What's wrong:** "Cost" and "Reversibility" are inverted (5 = cheap, 5 = easy to undo), and that meaning appears only on the create form.
- **Failure:** A user re-scoring cost in hindsight can read 5 as "expensive". That flips the delta sign and corrupts calibration and ranking.
- **Fix:** Pass the same hints in every `ScorePicker`, and document the scale meaning in the README.

### 21. Client requests have no network-error handling
- **Where:** `src/components/auth-form.tsx:26`, `idea-create-form.tsx:40`, `outcome-form.tsx:44`, `idea-detail.tsx:73-82`, `share-control.tsx:27-46`
- **What's wrong:**
  - `fetch` isn't wrapped in try/catch. If the network fails, the button stays on "Please wait…" or "Saving…" forever.
  - A failed delete or share action is silently ignored, so the UI doesn't reflect the failure.
  - Server-side Zod messages such as "Too small: expected string…" are shown directly to users.
- **Fix:** Add try/catch with an error state, and map validation errors to user-facing text.

### 22. Public share pages have no `noindex`, and a public endpoint duplicates the page
- **Where:** `src/app/s/[token]/page.tsx:12-22`, `src/app/api/share/[token]/route.ts`
- **What's wrong:**
  - The share page has no robots or `Referrer-Policy` metadata, and it queries the DB twice per request.
  - `/api/share/[token]` is not referenced anywhere in `src`. It is a second public data path that has to be kept in sync with the page.
  - Shared pages let anyone host arbitrary user content on your domain, with no report or takedown mechanism.
- **Failure:** Shared links posted publicly can be indexed. The unused endpoint can drift from the page, for example by returning fields the page hides. The user-content hosting is an abuse (spam or phishing) vector.
- **Fix:** Add `robots: { index: false }` and a no-referrer policy, remove or use the API route, and add an abuse or report path.

### 23. `next/font/google` needs network access at build time
- **Where:** `src/app/layout.tsx:2-14`
- **What's wrong:** Geist fonts are fetched from Google when building.
- **Failure:** The build may fail in offline or restricted CI (unconfirmed, since I couldn't build). It also adds an external dependency for reproducibility.
- **Fix:** Use `next/font/local`, or the `geist` package.

## Informational

### 24. Database design
- **Where:** `prisma/schema.prisma:55-56`, `prisma/migrations/20260917213700_score_checks/migration.sql`
- **What's wrong:**
  - `@@index([userId])` is redundant with `@@index([userId, status])`, since the composite index already covers `userId`.
  - The CHECK constraints from the second migration are not represented in `schema.prisma`. A `prisma db push` or a schema-only rebuild silently drops them, and the README claims they are enforced.
  - Text lengths (title 200, description 5000) are enforced only in Zod, not the database.
- **Fix:** Drop the redundant index and keep migrations as the source of truth.
  - Use `migrate deploy` everywhere.
  - Never use `db push` on real data.
  - Consider `VARCHAR(n)` or CHECK constraints for lengths.

### 25. Boilerplate and documentation issues
- **Where:** `public/*.svg` (`next.svg`, `vercel.svg`, `file.svg`, `globe.svg`, `window.svg` — none referenced in `src`), `src/app/favicon.ico`, `README.md:10`, `README.md:23-31`
- **What's wrong:**
  - The scaffold assets and default favicon are unused.
  - The README says "unshareable/unguessable" (a typo for "shareable"), and "Node 20+" contradicts finding 3.
  - The README has no production section, env-var table, threat model or note that rate limiting is absent.
- **Fix:** Remove the boilerplate, correct and expand the README, and add a `CONTRIBUTING`/`SECURITY` note.

### 26. Accessibility gaps
- **Where:** `src/components/ideas-dashboard.tsx:73-86`, `src/components/score-picker.tsx:26-43`
- **What's wrong:**
  - The status tabs are plain buttons with no `role="tab"`, `aria-selected` or `tablist`.
  - `ScorePicker` uses `role="radio"` without arrow-key handling or roving `tabindex`, so it doesn't follow the ARIA radio pattern.
  - The edit forms for idea title have no `required` or `maxLength`.
- **Fix:** Implement the ARIA tabs and radiogroup patterns, or use native radio inputs.
