# Pre-production review: Idea Log

I found nothing critical. I found 3 high, 12 medium, 15 low and 6 informational issues. No files were changed.

**What I could not verify:** `node_modules` is not installed, and installing would modify the tree. I did not run lint, typecheck or build. I could not read the bundled Next docs that `AGENTS.md` points to, so `proxy.ts` and `LayoutProps<"/">` were not checked against Next 16.3.5. `pnpm audit` ran fine and its output is in finding 20.

## High

**1. Placeholder or weak `JWT_SECRET` is accepted, and the README tells users to keep it**
- File: `src/lib/auth.ts:7-13`, `.env.example:2`, `README.md:27`
- The only check is `length >= 16`. The `.env.example` placeholder is 33 characters and passes. The README says "or keep the defaults".
- Failure: production is deployed with `change-me-to-a-long-random-string`. Anyone who knows that public string can sign an HS256 session for any user id. The attacker still needs a victim's user id, which is not exposed publicly. A secret shorter than 32 bytes is also weak for HS256.
- Fix:
  - Require at least 32 random bytes and reject the placeholder.
  - Validate at startup so the process refuses to boot, rather than failing per request.
  - Remove "keep the defaults" from the README and document `openssl rand -base64 48`.

**2. No rate limiting or lockout on login and register**
- File: `src/app/api/auth/login/route.ts:7-31`, `src/app/api/auth/register/route.ts:7-35`
- Failure:
  - An attacker can send unlimited password guesses against any email. The only password policy is 8 characters or more (`validation.ts:6`).
  - Unlimited registrations force a bcrypt cost-12 hash each (`auth.ts:21`), and `bcryptjs` is pure JS. That is a cheap CPU-exhaustion vector.
- Fix: rate-limit per IP and per email, with backoff or lockout. Add CAPTCHA or email verification on signup. Consider a native bcrypt or argon2.

**3. Account enumeration by response and by timing**
- File: `register/route.ts:19-25`, `login/route.ts:19-27`
- Register returns a distinct 409 for existing emails. Login skips the bcrypt compare when the user does not exist, so it responds much faster.
- Failure: an attacker can build a list of registered emails by probing either endpoint.
- Fix: always run a dummy `bcrypt.compare` on a miss. For register, return a generic response and use email verification.

## Medium

**4. Predictions can be rewritten after hindsight is recorded**
- File: `src/app/api/ideas/[id]/route.ts:37-40`, `src/lib/validation.ts:30-38`
- `PATCH` accepts changes to the four prediction scores at any time. The product's premise is comparing prediction against hindsight.
- Failure: after recording an outcome, a user edits `differentiation` from 2 to 5. The delta and the calibration summary silently change, and the original prediction is lost.
- Fix: make prediction scores immutable once `outcomeRecordedAt` is set, or keep a history of edits.

**5. Status, outcome and hindsight scores can become inconsistent**
- File: `[id]/route.ts:37-40`, `validation.ts:33`, `outcome/route.ts:26-37`
- The generic `PATCH` can set `status` to `ACTIVE`, `DONE` or `ABANDONED` without any outcome. There are no DB constraints tying `status`, `outcome` and the `h*` columns together.
- Failure:
  - `PATCH {status:"ACTIVE"}` on a finished idea leaves an outcome and hindsight scores on an ACTIVE idea. It still counts in calibration.
  - `PATCH {status:"DONE"}` on a new idea gives a DONE idea with no outcome.
- Fix: remove `status` from the generic update schema, or enforce the invariants in code and in a DB CHECK (all `h*` set or none, `outcome` set exactly when status is not ACTIVE).

**6. Sessions are stateless and cannot be revoked; there is no password change or reset**
- File: `src/lib/auth.ts:5,31-38`, `src/lib/session.ts:24-27`
- Logout only deletes the cookie. The JWT stays valid for 30 days.
- Failure: a stolen cookie keeps working after logout, after the user changes the password, or after they are locked out. The app has no password-change or reset flow at all, so a user who forgets a password loses the account.
- Fix: add a server-side session table or a `tokenVersion` on `User` that is checked in `getCurrentUser`. Add password change and email-based reset.

**7. Emails are never verified**
- File: `register/route.ts:27-32`
- Failure: anyone can register `victim@example.com` and hold that address. The real owner then gets "An account with that email already exists" and cannot sign up. This also enables abuse if email features are added later.
- Fix: verify email ownership before activating the account.

**8. No security headers**
- File: `next.config.ts:3-5`
- The config is empty. There is no CSP, `frame-ancestors` or X-Frame-Options, HSTS, `Referrer-Policy`, or `X-Content-Type-Options`. The `X-Powered-By` header is left on.
- Failure: the app can be framed for clickjacking against "Confirm delete" and "Revoke access". `/s/<token>` URLs can leak in Referer headers if external links are ever added.
- Fix: add a `headers()` config with these headers, set `poweredByHeader: false`, and set `Referrer-Policy: no-referrer` at least for `/s/*`.

**9. No tests and no CI**
- File: repository-wide. `package.json:5-13` has no test script and there are no test files.
- Untested paths: ownership scoping on every `/api/ideas/*` route, share-token lifecycle (create, rotate, revoke), score validation, `scoring.ts` and `calibration.ts` math, and the auth flows.
- Fix: add a test runner with API-level tests for cross-user access (user A gets 404 on user B's idea), plus unit tests for scoring and calibration. Add a CI workflow running lint, typecheck, tests, `pnpm audit` and build.

**10. No production deployment path**
- File: `package.json:12`, `README.md:64-65`, repository-wide
- There is no Dockerfile, CI, `migrate deploy` step or health endpoint. `db:migrate` runs `prisma migrate dev`, which is wrong for production. The README documents only local dev.
- Failure: the schema is not applied on deploy, or a dev-oriented command is run against the production DB.
- Fix: document and script `prisma migrate deploy`, add a Dockerfile (Next standalone output) and a `/api/health` route, and document required env vars.

**11. `docker-compose.yml` publishes Postgres with default credentials**
- File: `docker-compose.yml:6-10`
- `ports: "5432:5432"` binds all interfaces, and the credentials are `idealog/idealog`.
- Failure: if this file is used on a reachable host, the database is open with a guessable password.
- Fix: bind `127.0.0.1:5432:5432`, read the password from `.env`, and mark the file dev-only.

**12. Unhandled unique-constraint race on register**
- File: `register/route.ts:19-30`
- The route does a check-then-insert without catching Prisma `P2002`.
- Failure: two simultaneous signups with the same email both pass `findUnique`. The second `create` throws and returns an unhandled 500 instead of 409.
- Fix: drop the pre-check, or catch `P2002` and return 409.

**13. Login CSRF, and no Content-Type or Origin check on JSON routes**
- File: `login/route.ts:8` and all route handlers
- `req.json()` is called regardless of `Content-Type`. `SameSite=Lax` blocks most cross-site cookie use, but a cross-site `text/plain` form POST can still hit the unauthenticated login and register endpoints.
- Failure: an attacker logs the victim's browser into the attacker's account. The victim then stores ideas in it.
- Fix: require `application/json` and check the `Origin` or `Sec-Fetch-Site` header on state-changing routes.

**14. Unbounded ideas per user and no pagination**
- File: `src/app/api/ideas/route.ts:15-21`, `src/app/ideas/page.tsx:12-15`
- Both load every idea with `findMany` and no limit. Descriptions can be 5000 characters, and there is no per-user cap.
- Failure: with open signup and no rate limit, a user creates tens of thousands of ideas. The dashboard and API then return huge payloads and memory grows.
- Fix: paginate, cap ideas per user, and add rate limits on create.

**15. No backup or restore plan for user data**
- File: `docker-compose.yml:11-15`, README
- Data lives in one Docker volume. There is no backup or restore documentation, and delete is a hard delete.
- Fix: document backups and PITR for the production DB.

## Low

**16. `bcryptjs` and passwords over 72 bytes**
- File: `validation.ts:6,15`, `auth.ts:21`
- bcrypt only uses the first 72 bytes. The schema allows 200 characters.
- Failure: two passwords that differ only after byte 72 are treated as identical. I would need to confirm whether `bcryptjs` 3.x truncates silently or throws.
- Fix: cap at 72 bytes, or pre-hash.

**17. No request body size limit**
- File: all routes
- Zod caps field lengths only after the full body is parsed.
- Fix: enforce `Content-Length` limits at the reverse proxy or in the handler.

**18. Client fetch errors are unhandled**
- File: `src/components/auth-form.tsx:26-30`, `idea-create-form.tsx:40-44`, `outcome-form.tsx:44-48`, `idea-detail.tsx:57`
- These calls have no try/catch. A network error throws, and `loading` stays true, so the button stays disabled.
- Separately: `share-control.tsx:33-37,44-46` and `idea-detail.tsx:73-82` silently ignore failed responses. The user gets no feedback when share, revoke or delete fails.
- Fix: wrap calls in try/catch and surface an error in each component.

**19. No `error.tsx`, `not-found.tsx` or `global-error.tsx`**
- File: `src/app/`
- Failure: a DB outage on any page shows the framework default error. The API routes have no try/catch around Prisma calls, so failures surface as bare 500s with no structured log.
- Fix: add error boundaries and wrap route handlers with logging.

**20. High-severity advisory in the dependency tree**
- File: `package.json:21`, `pnpm-lock.yaml`
- `pnpm audit` reports `deepmerge-ts` below 8.0.0 (GHSA-ggr8-5vv4-36mx) through `prisma > @prisma/config`. It only matters if untrusted, recursive objects reach that merge. I do not see that path in this app.
- Fix: upgrade Prisma when a patched dependency is available, or use `pnpm.overrides`. Move the `prisma` CLI to `devDependencies` if `postinstall` allows.

**21. `prisma` and `@prisma/client` version ranges differ**
- File: `package.json:16,21`
- `@prisma/client` is `^6.19.3` and `prisma` is pinned to `6.19.3`. A client/CLI mismatch can break `generate`.
- Fix: pin both to the same exact version.

**22. Share responses have no cache or indexing controls**
- File: `src/app/api/share/[token]/route.ts:16`, `src/app/s/[token]/page.tsx:12-22`
- There is no `Cache-Control: no-store` and no `robots: noindex`.
- Failure: a CDN or browser can keep serving a revoked idea. A pasted public link can be indexed.
- Fix: add `no-store` and `noindex` on the share route and page.

**23. The public share API duplicates the page and is undocumented**
- File: `src/app/api/share/[token]/route.ts`, `src/app/s/[token]/page.tsx`
- The public endpoint has no consumer in the app, and the page queries the DB directly. That is two public exposure paths to keep in sync. `generateMetadata` and the page also each query the DB.
- Fix: remove the unused route or make the page share one function with it.

**24. Share link exposes outcome and hindsight, not just the idea**
- File: `api/share/[token]/route.ts:26-34`, `share-control.tsx:60`
- The UI says "view this idea", but outcome text and hindsight scores are also public.
- Fix: state this in the UI, or add an option to hide the outcome.

**25. `outcomeRecordedAt` is overwritten on every outcome edit**
- File: `outcome/route.ts:31`
- Failure: fixing a typo in the outcome resets the "Recorded" date. The original recording time is lost.
- Fix: set it only when it is null.

**26. CHECK constraints exist only in raw SQL**
- File: `prisma/migrations/20260917213700_score_checks/migration.sql:2-10`, `schema.prisma:36-47`
- The constraints are not expressed in `schema.prisma`. The next `migrate dev` may report drift, and `db push` or a reset from the schema alone loses them.
- Fix: document them in the schema, or use a Prisma feature that models them.

**27. Email uniqueness is case-sensitive at the database level**
- File: `schema.prisma:18`, `migration.sql:40`
- Lowercasing happens only in Zod, so any other insert path can create `A@x.com` and `a@x.com`.
- Fix: use `citext` or a unique index on `lower(email)`.

**28. Index redundancy and a missing sort index**
- File: `schema.prisma:55-56`
- `@@index([userId])` is redundant with `[userId, status]`. The list queries sort by `createdAt` for a user, so `[userId, createdAt]` would fit better.
- Fix: drop the single-column index and add `(userId, createdAt)`.

**29. No account deletion or data export**
- File: repository-wide
- Failure: a user cannot remove their account or take their data, which is a privacy-compliance gap.
- Fix: add self-service delete (the cascade already exists) and an export.

**30. Registration rejects whitespace-only names with a confusing error**
- File: `auth-form.tsx:24`, `validation.ts:11`
- The client sends `name: " "` because it is truthy. The server trims it and returns a raw Zod message such as "Too small: expected string to have >=1 characters".
- Fix: trim on the client. Map Zod issues to field-level messages. The same raw-message issue applies to all forms.

**31. No logging, metrics or health check**
- File: repository-wide; `prisma.ts:10` logs errors only
- Failure: failed logins, 5xx errors and share-link access leave no useful trace, and an orchestrator has no readiness probe.
- Fix: add structured logging and a health route.
