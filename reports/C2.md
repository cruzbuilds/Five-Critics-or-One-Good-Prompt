I reviewed all the source, ran `pnpm install`, `tsc`, `eslint`, `pnpm audit` and a full `next build`, and checked a few suspicions directly. I haven't run the app against a live Postgres or in a browser, so the runtime items below come from reading the code. I made no changes to tracked files.

## Fix before shipping

**1. The documented default `JWT_SECRET` is a public secret that passes validation.**
- The README says to fill in `.env.example` "or keep the defaults". Its value, `change-me-to-a-long-random-string`, is 33 characters, so it passes the `< 16` check in `src/lib/auth.ts:9`.
- Anyone who deploys with the default can have session tokens forged by anyone who has read the repo. A forged token only needs a victim's user id as `sub`.
- Fix: reject placeholder values, and require at least 32 random bytes in production. Validate at boot rather than per request. Today a missing secret throws inside `proxy.ts` on every `/ideas` request, so users get a 500.

**2. There is no brute-force or abuse protection on auth.**
- `/api/auth/login` and `/register` have no rate limiting or lockout.
- Each hash uses pure-JS `bcryptjs` at cost 12, which took about 400 ms of CPU per hash here. An unauthenticated caller can pin the server with register or login requests.
- Fix: rate-limit per IP and per account, and consider native `bcrypt` or argon2.

**3. Existing accounts can be detected.**
- Register returns a distinct 409 "account already exists" (`register/route.ts:21`).
- Login returns early with no bcrypt work when the user doesn't exist (`login/route.ts:20`), so response timing also reveals which emails are registered.
- Fix: compare against a dummy hash when the user is missing. Decide whether the 409 is acceptable for this product.

**4. Passwords longer than 72 bytes are silently truncated.**
- `passwordSchema` allows up to 200 characters, but bcrypt only uses the first 72 bytes. I confirmed a 72-byte password and the same password plus a different suffix both verify against one hash.
- Fix: cap at 72 bytes, or pre-hash.

**5. There is no production migration path.**
- The only migration script is `prisma migrate dev`, which is dev-only. There is no `migrate deploy` step, Dockerfile or CI.
- The README's deploy story is `pnpm dev`, or `build && start` with no database step.

**6. Sessions can't be revoked.**
- Logout only clears the cookie. The JWT stays valid for 30 days, and there is no server-side session or version check.
- There is also no password reset, email verification, password change or account deletion. Password change and reset are what would let users invalidate stolen tokens. Deletion and export matter if you hold real users' data.

**7. Zero tests and no CI.**
- The only commit is "raw generated build, unreviewed", and there is no `test` script.
- Highest-value tests: ownership checks on every `[id]` route, share-token revoke and rotate, and score validation.

## Should fix

**8. Prediction scores can be edited after the outcome is recorded.**
- `PATCH /api/ideas/[id]` accepts `differentiation`, `evidence`, `cost` and `reversibility` at any time, and keeps no history.
- That undermines the point of the app, which is comparing what you predicted with what happened. Decide whether predictions should lock once an outcome exists.

**9. `PATCH` accepts inconsistent states.**
- `ideaUpdateSchema` allows setting `status` to `DONE` or `ABANDONED` with no outcome or hindsight scores.
- It also allows setting it back to `ACTIVE` while the old outcome and hindsight scores remain. Calibration keys off `hindsightTotal != null`, not status, so such ideas still count.
- Fix: drop `status` from the generic update, or enforce the invariants.

**10. Ownership checks are separate from the writes.**
- Every route does `findFirst({id, userId})` and then `update/delete({where:{id}})`. It's safe today, but a concurrent delete gives an unhandled P2025 500, and one refactor could drop the check.
- Fix: use `updateMany` or `deleteMany` with `{id, userId}`.

**11. Registration has a race.**
- `findUnique` then `create` means two concurrent signups hit the unique constraint (P2002) and return an unhandled 500. Catch the error and return 409.
- No route wraps Prisma calls in try/catch, so any DB error is an opaque 500 with no logging.

**12. There are no security headers.**
- `next.config.ts` is empty, so there is no CSP, HSTS, `X-Frame-Options`/`frame-ancestors`, `Referrer-Policy` or `poweredByHeader: false`.
- The share page also has no `robots: noindex`, and its token sits in the URL. An "unlisted" link posted publicly can be indexed.

**13. Client error handling is thin.**
- Every `fetch` in the forms lacks try/catch, so on a network failure the button stays stuck on "Saving…" with no message.
- Delete (`idea-detail.tsx:79`) and all share-control actions fail silently. `navigator.clipboard` rejections are unhandled.

**14. Sharing exposes more than the UI says.**
- The `/s/[token]` page and `/api/share/[token]` include the outcome text and hindsight scores. The UI says only "anyone with the link can view this idea".
- Make that explicit, or add an option to share predictions only.

## Worth investigating or low priority

- **Hindsight tally on the dashboard:** every page renders `SiteHeader`, which reads the session and queries the DB, so every route is dynamic (the build output shows all routes as `ƒ`). The public share and marketing pages get a DB query per view and can't be cached.
- **No pagination:** `/ideas` and `GET /api/ideas` load all of a user's ideas, including 5,000-character descriptions and outcomes, and sort them in memory.
- **Possible hydration mismatch:** `share-control.tsx:18` branches on `typeof window`, so the server renders `/s/token` and the client renders the full URL. I couldn't check in a browser what the input shows after hydration.
- **`docker-compose.yml`:** Postgres is published on all interfaces with `idealog/idealog` credentials. Bind to `127.0.0.1` and make sure this file never reaches production.
- **`pnpm audit`:** one high advisory, `deepmerge-ts <8.0.0`, reached only through the Prisma CLI (`prisma > @prisma/config`). It is not in the runtime path, so it's low risk.
- **Small cleanups:**
  - `Idea_userId_idx` is redundant with `Idea_userId_status_idx`.
  - `jwtVerify` should pass `{ algorithms: ["HS256"] }` explicitly.
  - The `secure` cookie flag depends on `NODE_ENV`, so a plain-HTTP production deploy fails silently at login.
  - The proxy builds its redirect from `req.url`, which can be the wrong host behind some reverse proxies.
  - The README has a typo, "unshareable/unguessable".
  - `tsc --noEmit` alone fails on `LayoutProps` because that type is generated by `next build` or `next typegen`. Keep that in mind if CI runs `tsc` on its own.
- **`.claude/settings.json` (untracked):** it allows unprompted `npx`, `node`, `pnpm install` and `pnpm exec`. It also references `pytest`, `ruff` and `./scripts/check.sh`, which don't exist here. Don't commit it as is.

## What's fine

- Every idea route scopes by `userId`, and the public share endpoint uses an explicit field whitelist.
- The share token is `nanoid(24)`, roughly 144 bits, and revoke and rotate work.
- Zod strips unknown keys, so there is no mass assignment of `userId` or `shareToken`.
- I found no XSS sinks (`dangerouslySetInnerHTML` and similar).
- The session cookie is httpOnly with `sameSite=lax`.
- Score ranges are enforced in both Zod and DB CHECK constraints.
- Build and lint are clean.
