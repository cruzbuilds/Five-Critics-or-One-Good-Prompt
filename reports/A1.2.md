I reviewed the whole repository and found no critical issues, but there are two high-severity ones. I changed no files in the repo. I installed, type-checked, linted and built in a `git archive` copy under `/var/folders/.../tmp.GRlre6UbKX`. There was no database, so nothing was exercised at runtime beyond the build.

- **Build:** `next build` passes.
- **Lint:** eslint is clean.
- **Types:** `tsc` alone reports `LayoutProps` as undefined in `layout.tsx:21`. That is a generated global type and resolves during the build, so I did not count it.
- **Audit:** `pnpm audit` reports one high advisory (listed under Low).

## High

**1. The placeholder `JWT_SECRET` passes validation, so sessions can be forged**
- `src/lib/auth.ts:9`, `.env.example:2`, `README.md:27`
- The only check is `secret.length < 16`. The `.env.example` value `change-me-to-a-long-random-string` is 33 characters, and the README says "or keep the defaults".
- If production copies `.env.example`, anyone who has read this repo can sign an HS256 token with `sub` set to any user id. They then log in as any user and read, edit or delete that user's data. Cuids are not secret, and `email` is not checked against the database.
- Fix: refuse to start if the secret is the placeholder or under 32 random bytes. Remove the "keep the defaults" advice, document `openssl rand -base64 48`, and validate env vars once at boot.

**2. No rate limiting, and cost-12 bcryptjs blocks the event loop, so a few requests can stall the server**
- `src/app/api/auth/login/route.ts:24`, `src/app/api/auth/register/route.ts:27`, `src/lib/auth.ts:21`
- Login and register are unauthenticated and unthrottled. `bcryptjs` is pure JS. I measured about 500 ms per hash at cost 12. Four concurrent hashes took 1.6 s and produced about 400 ms of event-loop lag.
- A handful of parallel POSTs to `/api/auth/register` with valid-looking bodies keeps the single Node process busy, which stalls every route. The same endpoints allow unlimited password guessing and unlimited account creation.
- Fix: add per-IP and per-account throttling (edge or WAF, or a store-backed limiter). Switch to native `bcrypt`, `argon2` or `scrypt`, which run off the main thread. Add a CAPTCHA or invite gate on register.

## Medium

**3. Account enumeration via register responses and login timing**
- `register/route.ts:19-25`, `login/route.ts:19-27`
- Register returns a distinct 409 for existing emails. Login returns immediately for an unknown email but runs about 500 ms of bcrypt for a known one, despite the identical error text.
- An attacker can list which emails have accounts, then target them. This combines with finding 2.
- Fix: always run a bcrypt compare against a dummy hash for unknown users. For register, return a uniform response and require email verification.

**4. Status and outcome data can be made inconsistent, and predictions can be rewritten after the fact**
- `src/app/api/ideas/[id]/route.ts:37`, `src/lib/validation.ts:30-38`
- The generic PATCH accepts `status` and the four prediction scores independently of the outcome. I did not run these.
  - `{"status":"ACTIVE"}` on a finished idea leaves an ACTIVE idea with outcome and hindsight scores, which `computeCalibration` still counts.
  - `{"status":"DONE"}` produces a finished idea with no outcome.
  - `{"differentiation":5}` after the outcome is recorded rewrites the prediction that hindsight is compared against. The README says predictions are recorded at logging and the app exists to measure calibration.
- The outcome route also overwrites `outcomeRecordedAt` on every edit.
- Fix: make prediction scores immutable once an outcome exists. Only change `status` through the outcome endpoint, or reject reverting to ACTIVE. Add a DB CHECK that the four `h*` columns are all null or all set, and that `outcome` is set when `status <> 'ACTIVE'`. Keep the first `outcomeRecordedAt`.

**5. No password reset, email verification, or session revocation**
- Missing feature, related to `src/lib/auth.ts:5,31`
- Sessions are stateless 30-day JWTs, and logout only clears the browser cookie. A stolen token stays valid for the full 30 days, with no per-user invalidation.
- There is no password reset, so a user who forgets their password is locked out for good. Emails are unverified, so anyone can register an address they don't own.
- Fix: add email verification and a reset flow. Add a `sessionVersion` on `User` (or a session table) and check it in `getCurrentUser`. Consider a shorter TTL.

**6. No tests and no CI**
- Repo-wide. There is no test script or framework, and no `.github/` workflows or other CI.
- Nothing covers the ownership checks (the `userId` scoping in every `/api/ideas/*` route), share revoke and rotate, score bounds, calibration math, or the proxy. A regression in any of these would ship silently.
- Lint, typecheck and build are also not gated. The git history is a single commit, "raw generated build, unreviewed".
- Fix: add integration tests against a real Postgres for authz and IDOR, share lifecycle and validation. Run lint, `tsc`, tests and `next build` in CI.

**7. No production deployment or migration path**
- `package.json:13`, `README.md:25-31,64-65`
- The only migration script is `prisma migrate dev`, which is a development command that can prompt to reset the database. There is no `prisma migrate deploy` step, Dockerfile, hosting config, health check, backup guidance, or list of required env vars.
- A first deploy has no documented way to create the schema safely. Whoever improvises may run `migrate dev` against production.
- Fix: add a `db:deploy` script running `prisma migrate deploy` and run it in the release step. Add a Dockerfile or platform config (`output: "standalone"`), a `/healthz` route, and a deployment section in the README.

**8. Unbounded data: no pagination, no per-user limit, no body-size limit**
- `src/app/api/ideas/route.ts:15`, `src/app/ideas/page.tsx:12`
- Every list query loads all of a user's ideas, each up to 5000 characters of description, and sorts them in memory. The dashboard serialises all of them into the page.
- Because finding 2 lets accounts and ideas be created without limit, one account can bloat both the DB and the dashboard payload.
- Fix: add cursor pagination and `take` limits, and a per-user idea cap. Sort in SQL, and add an index such as `(userId, createdAt)`.

## Low

**9. Registration race returns a 500**
- `register/route.ts:19-30`
- The code does a check-then-create with no handling of a unique-constraint error. Two simultaneous registrations for one email make the second `create` throw `P2002`, which is an unhandled 500.
- Fix: catch `P2002` and return 409, or drop the pre-check.

**10. bcrypt silently truncates passwords at 72 bytes, but the schema allows 200**
- `src/lib/validation.ts:6`, `src/lib/auth.ts:21`
- I confirmed that a password differing only after byte 72 verifies successfully. Passwords with multibyte characters hit the limit sooner, at 36 two-byte characters.
- A user with a long passphrase gets less entropy than they think.
- Fix: cap the password at 72 bytes and say so, or pre-hash with SHA-256 before bcrypt. Argon2 (finding 2) removes the limit.

**11. Missing security headers and no origin check on mutating routes**
- `next.config.ts` is empty; the mutating routes are under `src/app/api/**`.
- There is no CSP, `frame-ancestors`, `X-Content-Type-Options`, `Referrer-Policy` or HSTS, and the `X-Powered-By` header is on. JSON routes do not check `Content-Type` or `Origin`.
- The only CSRF defence is `SameSite=Lax`, which also blunts clickjacking. A future subdomain or a change to the cookie setting would remove that protection.
- Fix: set headers in `next.config.ts` or the proxy, set `poweredByHeader: false`, and reject mutating requests whose `Origin` does not match.

**12. Shared-link page is indexable and can leak the token by `Referer`**
- `src/app/s/[token]/page.tsx:12-22`
- There is no `robots: noindex` and no `Referrer-Policy: no-referrer`. The token is the only secret in the URL.
- A link pasted anywhere public can be crawled, and any link a viewer follows from the page sends the token in `Referer`. The owner's "Revoke access" is the only recourse.
- Fix: add `robots: { index: false }` and `referrer: "no-referrer"` metadata.
- Related, and worth confirming as a product decision: sharing also exposes the private `outcome` and hindsight scores. The share UI says only "view this idea", so the copy should say what is exposed.

**13. A missing or invalid `JWT_SECRET` fails silently**
- `src/lib/auth.ts:44-51`, `src/proxy.ts:11`
- `getSecretKey()` runs inside the `try` in `verifySessionToken`, so a bad secret is swallowed as "no session". Every user is bounced to `/login`, while login itself 500s from `createSessionToken`, with no clear error logged.
- Fix: validate env vars at startup and fail loudly.

**14. Client-side error handling is missing in several places**
- `auth-form.tsx:26`, `idea-detail.tsx:57,75`, `share-control.tsx:27-46`, `logout-button.tsx:13`
- A network failure makes `fetch` throw, and the buttons stay stuck ("Please wait…", "Saving…").
- A failed delete, share, rotate or revoke shows no message. A failed share revoke looks like nothing happened, so the owner may believe the link is dead when it is still live.
- Fix: wrap calls in try/catch and show errors. Handle 401 by redirecting to login.

**15. Dependency issues**
- `package.json:16,21,37`
- `pnpm audit` reports a high advisory (GHSA-ggr8-5vv4-36mx, stack exhaustion in `deepmerge-ts` <8) via `prisma > @prisma/config`. It is reachable only through the Prisma CLI, which runs only if you run migrations in production, not at request time.
- `@prisma/client` is `^6.19.3` while `prisma` is pinned at exactly `6.19.3`, so the client and CLI can drift apart.
- Fix: pin both to the same version and upgrade Prisma when a patched release is available.

**16. Runtime version guidance is stale**
- `README.md:23`, `package.json:28`
- The README says "Node 20+" and `@types/node` is `^20`. Node 20 reached end-of-life in April 2026 (my recollection, worth checking). There is no `engines` field or `.nvmrc`. Next 16.3.5 itself requires `>=20.9`.
- Fix: target Node 22 or 24 and add `engines` and `.nvmrc`.

**17. Compose exposes Postgres on all interfaces with a default credential**
- `docker-compose.yml:6-10`
- `"5432:5432"` binds `0.0.0.0` with `idealog:idealog`. On a shared network or a reused server, that is a reachable database with a public password. There is no healthcheck.
- Fix: bind to `127.0.0.1:5432:5432`, read the password from `.env`, and add a healthcheck.

**18. Weak DB constraints and one redundant index**
- `prisma/schema.prisma:55-56`, `prisma/migrations/*`
- `@@index([userId])` is redundant with `[userId, status]`. Title and description lengths are enforced only in the app. There is no DB rule that a `shareToken` is non-empty.
- Fix: drop the redundant index and add the consistency CHECKs from finding 4. The migration-only CHECK constraints are not visible in `schema.prisma`, so note them there or in the README.

**19. Redirect built from `req.url`**
- `src/proxy.ts:14`
- Behind a reverse proxy that does not preserve the host, this can redirect to an internal origin such as `localhost:3000`. I have not confirmed this in a proxied deployment.
- Fix: use `req.nextUrl.clone()` with `pathname = "/login"`.

**20. Accessibility gaps**
- `src/components/score-picker.tsx:26-43`, `outcome-form.tsx:64`, `share-control.tsx:72`
- The radio group has no roving tabindex or arrow-key handling, so it is a four-button tab stop per row. The "What happened?" label is not tied to its controls, and the readonly share URL input has no label.
- Fix: use native radio inputs, or implement the ARIA radiogroup keyboard pattern, and add labels.

## Informational

**21. Every page renders dynamically, and the API has dead surface**
- Root layout: `src/components/site-header.tsx:6` calls `getCurrentUser()`, which reads cookies and hits the DB, from the root layout.
  - Every route becomes dynamic. The build shows `ƒ` for all of them, including the marketing page and the public share page, so nothing is static or cacheable.
  - Every page view costs one DB query.
- Dead API: `GET /api/auth/me`, `GET /api/ideas`, `GET /api/ideas/[id]` and `GET /api/share/[token]` are not called by the UI.
  - `/api/share/[token]` duplicates the field selection in `s/[token]/page.tsx`, and `PublicIdeaDTO` in `types.ts:28` is unused. The two copies could drift, and a new field on one could leak.
- Fix: read the session only where needed, and share one public serializer or remove the dead routes.

**22. No account deletion or data export, no error boundaries, no logging or monitoring, no license or privacy documentation**
- There is no `error.tsx` or `global-error.tsx`, and no structured logging. Prisma errors are not caught anywhere, so DB failures surface as bare 500s.
- Users cannot delete their account or export their data.
- Fix: add these before launch if you serve real users, especially in regulated regions.

**23. README inaccuracies**
- `README.md:10`
- "unshareable/unguessable link" should read "unguessable". The README also gives no production instructions, no env-var table, and no test instructions.

**24. Untracked `.claude/settings.json` is a template carried over from another project**
- `.claude/settings.json`
- It auto-allows arbitrary code execution: `Bash(node:*)`, `Bash(npx:*)`, `Bash(pnpm exec:*)` and `Bash(pnpm install:*)`. It also references tools and a script that don't exist here (`pytest`, `ruff`, `checkov`, `./scripts/check.sh`).
- `.claude/` is not in `.gitignore`, so it could be committed by accident. Committing it would grant those permissions to anyone who clones the repo and uses Claude Code.
- Fix: prune it, or add it to `.gitignore`.

Nothing else I checked was a problem. Every `/api/ideas/*` route scopes by `userId`, so there is no cross-user access. Zod strips unknown keys, so there is no mass assignment. React escapes all rendered user content, there is no `dangerouslySetInnerHTML`, and there is no SQL injection since Prisma parameterises everything. Share tokens are 144-bit `nanoid(24)` values, and revocation takes effect immediately.
