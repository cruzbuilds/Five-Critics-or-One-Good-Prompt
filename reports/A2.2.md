## High

### H1. The placeholder `JWT_SECRET` passes validation, so sessions can be forged
- **Where:** `.env.example:2`, `src/lib/auth.ts:9`, `README.md:27`
- **Problem:** `getSecretKey()` only checks `length >= 16`. The example value `change-me-to-a-long-random-string` is 33 characters and passes. The README says to "keep the defaults".
- **Failure:** A deployment that copies `.env.example` (or any short guessable secret) is signed with a publicly known key. I forged a token with `sub` set to an arbitrary user id and `jwtVerify` accepted it. Anyone who knows or guesses a victim's user id can then impersonate them, with the full 30-day lifetime. Prisma's default `cuid()` ids are not high-entropy, so guessing is not far-fetched.
- **Fix:** Require at least 32 bytes of entropy and reject known placeholders, at process start rather than on first login. Remove "or keep the defaults" from the README. Ship `.env.example` with an empty `JWT_SECRET=` and a `openssl rand -base64 48` hint.

### H2. No rate limiting on auth endpoints, which allows credential stuffing and CPU exhaustion
- **Where:** `src/app/api/auth/login/route.ts:7`, `src/app/api/auth/register/route.ts:7`, `src/lib/auth.ts:21`
- **Problem:** There is no per-IP or per-account throttle, lockout or CAPTCHA. Hashing uses pure-JS `bcryptjs` at cost 12, which took about 400 ms of Node event-loop CPU per hash in my test.
- **Failure:**
  - An attacker can try passwords against a known email without limit.
  - A few dozen concurrent `POST /api/auth/register` or `/login` requests keep the single Node thread busy hashing. Every other request, including the public share pages, stalls.
  - Registration is open, so this also lets someone create unlimited accounts.
- **Fix:**
  - Add rate limiting in front of the app (reverse proxy or WAF) and in the handlers, keyed on IP and email.
  - Add exponential backoff or lockout on repeated failures.
  - Use native `bcrypt` or `argon2` so hashing runs off the event loop.
  - Consider email verification or a CAPTCHA on register.

## Medium

### M1. An idea's prediction scores can be rewritten after the outcome, which corrupts the calibration data
- **Where:** `src/app/api/ideas/[id]/route.ts:37-40`, `src/lib/validation.ts:30-38`, `src/components/idea-detail.tsx:119-122`, `src/lib/calibration.ts:15`
- **Problem:** `PATCH /api/ideas/[id]` accepts `differentiation`, `evidence`, `cost` and `reversibility` at any time. The Edit button is always shown, and `status` is also settable there without an outcome.
- **Failure:**
  - After recording hindsight, the user can edit the original prediction to match what happened. The "were you right?" delta then reads ±0, which defeats the product's purpose.
  - `PATCH {status:"DONE"}` creates a DONE idea with no outcome.
  - `PATCH {status:"ACTIVE"}` on a finished idea leaves the hindsight scores in place. `computeCalibration` filters on `hindsightTotal != null`, not on status, so ACTIVE ideas still feed the calibration stats.
- **Fix:** Reject prediction-score edits once `outcomeRecordedAt` is set, or store predictions immutably and keep a history. Remove `status` from `ideaUpdateSchema`, since it should change only via the outcome route. Decide what reopening does (clear or keep hindsight) and enforce it in one place.

### M2. Sessions cannot be revoked, and there is no password reset or change
- **Where:** `src/lib/auth.ts:5,31-38`, `src/lib/session.ts:24-27`
- **Problem:** The session is a stateless 30-day JWT. Logout only deletes the browser cookie. There is no session id, `tokenVersion` or denylist, and no password-change or forgot-password flow exists.
- **Failure:**
  - A stolen cookie stays valid for 30 days after logout.
  - Nothing invalidates other sessions if an account is compromised.
  - A user who forgets their password is permanently locked out.
- **Fix:** Add a `sessionVersion` on `User` (checked in `getCurrentUser`) or a sessions table. Bump it on logout-everywhere and on password change. Add password change and email-based reset. Consider a shorter TTL with refresh.

### M3. No security headers
- **Where:** `next.config.ts:3-5` (empty config)
- **Problem:** No CSP, HSTS, `X-Frame-Options` / `frame-ancestors`, `X-Content-Type-Options`, `Referrer-Policy` or `Permissions-Policy`. `X-Powered-By` is still sent.
- **Failure:** The app can be framed (clickjacking the delete and share buttons). There is no CSP backstop if an XSS ever appears. Share URLs (`/s/<token>`) can leak through the `Referer` header to any external link or resource.
- **Fix:** Add `headers()` in `next.config.ts` (or set them at the edge), set `poweredByHeader: false`, and use `Referrer-Policy: no-referrer` at least on `/s/*`.

### M4. Auth POSTs accept any Content-Type and have no Origin check, which allows login CSRF
- **Where:** `src/app/api/auth/login/route.ts:8`, `src/app/api/auth/register/route.ts:8`
- **Problem:** `req.json()` parses the body regardless of `Content-Type`. `SameSite=Lax` protects authenticated mutations but not the login and register requests, which carry no cookie.
- **Failure:** An attacker page can submit a cross-site `<form enctype="text/plain">` whose body is valid JSON to `/api/auth/login`. The response's `Set-Cookie` is accepted on a top-level navigation. The victim is silently signed into the attacker's account and may then store private ideas there.
- **Fix:** Require `Content-Type: application/json` and verify `Origin` / `Sec-Fetch-Site` matches the app on all state-changing routes.

### M5. No tests and no CI
- **Where:** `package.json:5-13` (no `test` script), no test files, no workflow
- **Problem:** Ownership scoping (`findFirst({id, userId})`), zod validation, scoring and calibration math, share revoke/rotate, and the proxy redirect are all unverified. Nothing gates a merge on lint, typecheck or build.
- **Failure:** A regression such as a dropped `userId` filter, a bad delta sign or a broken revoke ships silently. The commit message is "raw generated build, unreviewed".
- **Fix:**
  - Add unit tests for `scoring` and `calibration`.
  - Add integration tests against a real Postgres for every route: cross-user access returns 404, a revoked token returns 404, invalid scores return 400.
  - Add a CI job running lint, `next typegen` + `tsc`, tests and build.

### M6. No production deployment path
- **Where:** `package.json:11` (`db:migrate` = `prisma migrate dev`), `docker-compose.yml:5-10`, `README.md:64-65`
- **Problem:**
  - There is no Dockerfile, no deploy documentation and no `prisma migrate deploy` step. `migrate dev` is for development and may prompt to reset the database.
  - The compose file is dev-only, but nothing says so in the file itself. It uses the credentials `idealog/idealog`, publishes 5432 on all interfaces, and has no healthcheck.
- **Failure:** An operator following the README either has no schema in production or runs `migrate dev` against it. If the compose file is reused, an internet-reachable Postgres with a trivially guessable password results.
- **Fix:** Add a documented release step (`prisma migrate deploy`), a Dockerfile (ideally `output: "standalone"`), and a separate prod config. Bind the dev DB to `127.0.0.1` and label it dev-only. Require non-default DB credentials in production.

### M7. No error handling, error pages, logging or health check
- **Where:** all `src/app/api/**` (no `try/catch` around Prisma calls); no `error.tsx`, `global-error.tsx` or `not-found.tsx` in `src/app`; no health route
- **Problem:** A DB outage or unexpected exception returns an opaque 500 with no structured log. There is no monitoring hook and no readiness endpoint.
- **Failure:** On a DB blip, users get a bare Next error page. Operators have no signal, and the orchestrator cannot tell whether the app is ready.
- **Fix:** Wrap handlers in a shared error helper that logs with a request id and returns JSON errors. Add error boundaries and a `/api/health` that checks the DB. Wire in error tracking.

### M8. No pagination, per-user quota or body-size limit
- **Where:** `src/app/api/ideas/route.ts:15-21`, `src/app/ideas/page.tsx:12-15`, plus every `req.json()`
- **Problem:** Each list loads every idea, including 5000-character descriptions, and sorts in JS. There is no cap on ideas per user, and request bodies are read unbounded before zod's length checks.
- **Failure:** With open registration and no throttle, one script can fill the database. It can also create an account whose dashboard SSR and JSON payload grow without limit.
- **Fix:** Paginate or cursor the list and sort in SQL. Cap ideas per user. Enforce a request body size limit before parsing.

## Low

### L1. bcrypt silently truncates passwords over 72 bytes
- **Where:** `src/lib/validation.ts:6`, `src/lib/auth.ts:21-28`
- **Problem:** The schema allows 200 characters, but bcrypt ignores everything past byte 72.
- **Failure:** Confirmed: two passwords sharing the first 72 bytes both verify. A user relying on a long passphrase gets less protection than they think.
- **Fix:** Cap at 72 bytes, or pre-hash (SHA-256, then base64) or switch to argon2.

### L2. Account enumeration via the register response and login timing
- **Where:** `register/route.ts:19-25` (409 "already exists"), `login/route.ts:19-26`
- **Problem:** Register reveals which emails exist. Login skips bcrypt for unknown emails, so those requests return measurably faster.
- **Failure:** An attacker can build a list of valid emails for stuffing or phishing.
- **Fix:** Run a dummy `bcrypt.compare` for unknown users. For register, use a generic response plus email verification.

### L3. Register has a race condition and can create a user then fail
- **Where:** `src/app/api/auth/register/route.ts:19-32`
- **Problem:** The check-then-insert is not atomic, so a concurrent duplicate hits the unique index and throws an unhandled `P2002` (500). Separately, `setSessionCookie` can throw (for example a bad `JWT_SECRET`) after the user row is created.
- **Failure:** A double-click or two tabs give a 500 rather than 409. With a bad secret, registration returns 500 but the account exists, and a retry says "already exists".
- **Fix:** Catch `P2002` and return 409. Validate env at boot (L6).

### L4. Shared-idea pages and API lack robots, cache and referrer hygiene
- **Where:** `src/app/s/[token]/page.tsx:7-22`, `src/app/api/share/[token]/route.ts:9-37`
- **Problem:**
  - There is no `robots: noindex` metadata and no `Cache-Control: no-store` on the JSON endpoint.
  - Both `generateMetadata` and the page query the DB separately for the same token.
  - The token is stored in plaintext.
  - The public endpoint is unthrottled.
- **Failure:**
  - A share URL that lands somewhere crawlable gets indexed. A CDN could cache a revoked idea.
  - A DB read leak exposes every live share link.
- **Fix:** Add `robots: {index:false}`, `no-store` and `Referrer-Policy: no-referrer`. Wrap the lookup in `React.cache`. Store a hash of the token. Rate-limit the endpoint.

### L5. No account deletion, data export or privacy and terms pages
- **Where:** absent (no route, no UI)
- **Problem:** Users can delete ideas but not their account. There is no privacy policy or terms.
- **Failure:** Users cannot leave or erase their data, which can breach GDPR/CCPA erasure obligations. Nothing covers abuse of the public share pages, which are free-text hosting.
- **Fix:** Add account deletion (the cascade already exists), export, policy pages, and a report or takedown route.

### L6. Environment is not validated at startup
- **Where:** `src/lib/auth.ts:7-13`, `src/lib/prisma.ts`, `.env.example`
- **Problem:** A missing or short `JWT_SECRET` throws only inside the first request that signs or verifies a token. Because `verifySessionToken` swallows the error, the proxy fails closed and just redirects to login.
- **Failure:** A misconfigured deploy looks healthy and then silently refuses every login. Operators see redirects rather than a config error.
- **Fix:** Validate `DATABASE_URL` and `JWT_SECRET` once at boot (zod env schema or `instrumentation.ts`) and exit non-zero.

### L7. JWT verification does not pin the algorithm
- **Where:** `src/lib/auth.ts:44`
- **Problem:** `jwtVerify` is called without `algorithms: ["HS256"]`, and `issuer` and `audience` are not set.
- **Failure:** Currently mitigated by the symmetric-key type (jose rejects other algorithms), so low. It would matter if keys or usage ever change.
- **Fix:** Pass `{ algorithms: ["HS256"], issuer, audience }`.

### L8. Database design gaps
- **Where:** `prisma/schema.prisma:55-56`, `prisma/migrations/20260917213700_score_checks/migration.sql:2-10`, `schema.prisma:18`
- **Problem:**
  - The `[userId]` index is redundant with the `[userId, status]` composite.
  - Nothing enforces that hindsight scores are all set or all null, or that `outcome` is set only when status is not ACTIVE.
  - The CHECK constraints live only in a hand-written migration, not in `schema.prisma`, so `prisma db push` or a re-baseline drops them without warning.
  - Email uniqueness is case-sensitive at the DB level and relies on app lowercasing.
- **Failure:** Inconsistent rows (see M1) are accepted by the DB. A `db push` environment loses the score ranges.
- **Fix:**
  - Drop the redundant index.
  - Add a CHECK for the hindsight and status invariant.
  - Use `citext` for email, or a lowercase unique index.
  - Document that constraints are migration-only.

### L9. Silent failures in client actions
- **Where:** `src/components/idea-detail.tsx:73-82`, `share-control.tsx:33-37,44-46,49-53`, `auth-form.tsx:26-30`, `idea-create-form.tsx:37-45`
- **Problem:**
  - Delete, share, revoke and rotate show nothing on failure.
  - Clipboard rejection is unhandled.
  - `fetch` calls in the forms have no `try/catch`, so a network error leaves the button stuck on "Please wait…".
- **Failure:** A user believes a share link was revoked when the request failed (a privacy-relevant mistake), or the UI hangs offline.
- **Fix:** Wrap the calls, surface an error, and reset the loading state in `finally`.

### L10. API error messages are raw zod text
- **Where:** all routes (`parsed.error.issues[0]?.message`)
- **Problem:** Only the first issue is returned, and it does not name the field (for example "Too small: expected string to have >=1 characters").
- **Failure:** Users cannot tell which input to fix.
- **Fix:** Return `{field, message}` for all issues.

### L11. `tsc` fails on a clean checkout
- **Where:** `src/app/layout.tsx:21` (`LayoutProps`), `.gitignore` (`next-env.d.ts`)
- **Problem:** `LayoutProps<"/">` is a generated global type. `tsc --noEmit` gives `TS2304: Cannot find name 'LayoutProps'` until `next dev`, `next build` or `next typegen` has run.
- **Failure:** A CI typecheck step run before the build fails for a non-bug.
- **Fix:** Run `next typegen` first in CI, or document the order.

### L12. Dependency and manifest hygiene
- **Where:** `package.json:14,24`, `pnpm-lock.yaml`
- **Problem:**
  - `pnpm audit` reports one high advisory (GHSA-ggr8-5vv4-36mx, `deepmerge-ts <8`) via `prisma > @prisma/config`. It is a CLI/tooling path and not reachable at request time, but `prisma` is listed in `dependencies`, so it ships to production.
  - `@prisma/client` is `^6.19.3` while `prisma` is exact `6.19.3`. A future `pnpm update` can desync them.
  - There is no `engines` or `.nvmrc` (README says Node 20+, and Next 16 needs at least 20.9).
- **Failure:** Audit gates in CI fail. Client/CLI version skew breaks `prisma generate`.
- **Fix:** Move `prisma` to `devDependencies` (keep `generate` in the build step), pin both Prisma packages identically, add `engines`, and re-audit when Prisma ships a fix.

### L13. The site header runs a DB lookup on every page, including public pages
- **Where:** `src/components/site-header.tsx:6`, `src/app/layout.tsx:28`
- **Problem:** The root layout calls `getCurrentUser()`, which uses `cookies()` and a Prisma query. Every route becomes dynamic (the build shows all routes as `ƒ`), including the marketing page and `/s/*`.
- **Failure:** No static or CDN caching, and a DB query per view of a public link. A viewer who is logged in also sees their own email in the header of someone else's shared idea.
- **Fix:** Verify the JWT only for the header (no DB hit), or move the auth-aware nav into a client component or `Suspense` island so public pages can be static.

### L14. Re-editing an outcome resets `outcomeRecordedAt`
- **Where:** `src/app/api/ideas/[id]/outcome/route.ts:31`
- **Problem:** Every PATCH sets `outcomeRecordedAt: new Date()`, including when only a typo is fixed.
- **Failure:** "Recorded <date>" drifts forward and no longer reflects when the outcome was originally logged.
- **Fix:** Set it only when it is currently null.

### L15. Build depends on the Google Fonts network
- **Where:** `src/app/layout.tsx:2-14`
- **Problem:** `next/font/google` fetches fonts at build time.
- **Failure:** Air-gapped or restricted CI runners fail the build (it worked here).
- **Fix:** Self-host via `next/font/local`, or accept and document the dependency.

## Informational

- **I1. `.claude/settings.json` is untracked and does not match the project.** It allows `pytest`, `ruff` and `./scripts/check.sh` (none exist here). It also allows `npx:*`, `node:*` and `pnpm install:*`, which permit arbitrary code execution without a prompt. That is fine locally, but review it before committing, and do not treat the deny list as a boundary.
- **I2. README gaps.**
  - Line 11 says "unshareable/unguessable" where "unlisted" is meant.
  - The README has no production or deployment section, no environment variable reference (`JWT_SECRET` minimum, `NODE_ENV` and the cookie `secure` flag), no threat model or auth limitations, no API docs and no operational runbook.
  - The claim about proxy protection is accurate for `/ideas*` pages only. `/api/*` relies entirely on the per-route `requireUser()` calls, so a new route that forgets it is open. Consider a shared wrapper.
- **I3. Session cookie hardening.** `secure` depends on `NODE_ENV === "production"`, so `next start` behind plain HTTP silently sets a non-secure cookie. Consider a `__Host-` prefix. No `LICENSE` file.
- **I4. Public share pages are user-generated content.** Text is rendered as plain React text (no XSS), but anyone can publish up to 5,000 characters at a URL on your domain. That is a phishing and abuse surface (see L5).
- **I5. Not verified.**
  - I did not run the app against a live database, so `P2002` behaviour, the CHECK constraints and cascade deletes are assessed by reading the code only.
  - I did not test the proxy redirect behaviour at runtime.
  - I only skimmed the Next 16 `proxy.ts` docs, but the build accepted it.
