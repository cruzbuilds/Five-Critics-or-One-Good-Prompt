# Pre-production review: Idea Log

I found no confirmed critical issues. The ownership checks on every idea route (`findFirst({ id, userId })`) are sound, and I found no IDOR. But the repo is a single commit labelled "raw generated build, unreviewed". It has no tests and no production deployment path, and it has no protection against password guessing.

**Limits of this review:**
- I read every tracked file and changed nothing.
- `node_modules` isn't installed, so I did not run `build`, `lint` or `tsc`.
- I could not run `pnpm audit` because the shell blocked it, so dependency CVEs are unchecked. The lockfile does match `package.json`.
- I could not check the Next 16 docs in `node_modules/next/dist/docs/`, as `AGENTS.md` says to do.

## High

**1. The placeholder `JWT_SECRET` passes validation, and the README says to keep it**
- **Where:** `.env.example:2`, `src/lib/auth.ts:9`, `README.md:27`
- **Problem:** The only check is `length >= 16`. The example value `change-me-to-a-long-random-string` is 33 characters, so it passes. The README says to "keep the defaults".
- **Failure:** If production runs with the example value, anyone can sign an HS256 token with `sub = <any user id>` and be logged in as that user. Exploiting it needs a valid user id, which is a cuid, so it is conditional on the config mistake rather than trivial.
- **Fix:**
  - Require at least 32 random bytes and reject known placeholder strings.
  - Validate all env vars once at startup so the app fails to boot.
  - Remove "keep the defaults" from the README and document `openssl rand -base64 48`.

**2. No rate limiting or brute-force protection on login and register**
- **Where:** `src/app/api/auth/login/route.ts:7`, `src/app/api/auth/register/route.ts:7`, `src/lib/auth.ts:21`
- **Problem:** There is no throttle, lockout or CAPTCHA, and the password policy is only 8 characters.
- **Failure:**
  - An attacker can run unlimited credential-stuffing against `/api/auth/login`.
  - Anyone can flood `/api/auth/register`. Each call runs `bcryptjs` at cost 12, which is pure JavaScript on the Node process. A modest request rate can starve CPU for every user.
  - Nothing caps how many accounts or ideas one client can create.
- **Fix:**
  - Rate-limit by IP and by account, ideally at the edge or with a shared store such as Redis.
  - Add a lockout or backoff after repeated failures.
  - Consider the native `bcrypt`, or argon2, so hashing doesn't block the event loop.

## Medium

**3. No production deployment path**
- **Where:** `package.json:6-14`, `README.md:21-31,64-65`
- **Problem:** The only migration script is `prisma migrate dev`, which is a development command that can prompt and reset. There is no `prisma migrate deploy` script, no Dockerfile, no CI, no health endpoint and no documented production procedure.
- **Failure:** Someone following the README on a server either runs `migrate dev` against production or has no documented way to apply the CHECK-constraint migration.
- **Fix:** Add `db:deploy` (`prisma migrate deploy`) and a build and deploy pipeline. Add a `/healthz` route. Document required env vars, HTTPS (the cookie is `secure` only when `NODE_ENV=production`), backups and rollback.

**4. No tests, no test script, no CI**
- **Where:** `package.json` (no `test` or `typecheck` script), no test files
- **Problem:** Nothing tests authorization (cross-user access on each route), validation, the scoring and calibration maths, or the share-token lifecycle (create, rotate, revoke).
- **Failure:** A future refactor that drops `userId` from one `where` clause ships silently and exposes another user's ideas.
- **Fix:**
  - Add integration tests for every route, including 401 and 404 on other users' ideas and a revoked share token returning 404.
  - Unit-test `scoring.ts` and `calibration.ts`.
  - Run lint, typecheck, tests and `pnpm audit` in CI.

**5. Prediction scores and status can be rewritten after the outcome, which corrupts the calibration feature**
- **Where:** `src/lib/validation.ts:30-38`, `src/app/api/ideas/[id]/route.ts:37-40`, `src/components/idea-detail.tsx:120`, `src/lib/calibration.ts:15`
- **Problem:** `PATCH /api/ideas/[id]` accepts any combination of scores and `status`. Nothing locks the original predictions once hindsight is recorded, and no rule ties status to outcome.
- **Failure:**
  - A user marks an idea DONE with no outcome.
  - A user sets an idea back to ACTIVE, leaving stale hindsight scores. Calibration still counts it because it filters on `hindsightTotal != null`, not on status.
  - A user edits the "predicted" scores after seeing the result. The "how wrong was I" metric then reports whatever the user wants.
- **Fix:**
  - Make predictions immutable once an outcome exists, or store a revision history.
  - Enforce state transitions: `status` should only leave ACTIVE through the outcome endpoint.
  - Add DB CHECKs (see finding 9).

**6. Sessions can't be revoked**
- **Where:** `src/lib/session.ts:24-27`, `src/lib/auth.ts:5,44`
- **Problem:** Sessions are stateless 30-day JWTs. Logout only deletes the browser cookie. There is no server-side session record, no token version, and no change-password or reset flow to invalidate anything.
- **Failure:** A stolen cookie or token stays valid for up to 30 days after the user logs out. Nothing can end it except deleting the account.
- **Fix:** Store sessions in the DB, or add a `tokenVersion` column on `User` that is checked in `getCurrentUser`. Shorten the TTL. Add change-password, which bumps the version.

**7. No security headers**
- **Where:** `next.config.ts:3-5`
- **Problem:** The config is empty, so there is no CSP, `X-Frame-Options` or `frame-ancestors`, `Referrer-Policy`, `X-Content-Type-Options` or HSTS.
- **Failure:** Another site can frame `/ideas/[id]` and clickjack the "Confirm delete" and "Create share link" buttons. The share token sits in the URL of `/s/<token>`, with no `Referrer-Policy` to stop it leaking on outbound navigation.
- **Fix:** Add a `headers()` block with a CSP, `frame-ancestors 'none'`, `Referrer-Policy: no-referrer` (at least for `/s/*`), `nosniff` and HSTS.

**8. Unhandled errors and no error pages**
- **Where:** all `src/app/api/**/route.ts`. There is no `error.tsx`, `not-found.tsx` or `global-error.tsx` anywhere in `src/app`.
- **Problem:** No Prisma call is wrapped in try/catch.
- **Failure:**
  - **Register race:** `register/route.ts:19-30` does check-then-create. Two concurrent registrations for one email make the second `create` throw a unique-violation (P2002), which surfaces as a bare 500 instead of the 409.
  - **Missing secret:** With `JWT_SECRET` missing, `register` creates the user and then `setSessionCookie` throws (`auth.ts:9`). The user gets a 500 but the account exists.
  - **Silent logout:** `verifySessionToken` catches everything, including the missing-secret error, so every request looks logged out with no log line.
- **Fix:** Catch P2002 and return 409, or use an upsert-style flow. Wrap handlers or add a shared error helper that logs and returns JSON. Add `error.tsx` and `not-found.tsx`. Fail at startup on a bad secret.

**9. Database integrity gaps**
- **Where:** `prisma/schema.prisma:41-47`, `prisma/migrations/20260917213700_score_checks/migration.sql`
- **Problem:** The DB allows `outcome` set with a partially null hindsight set, hindsight scores with `status = ACTIVE`, and `status = DONE` with no outcome. Title and description lengths are enforced only in Zod, and the column types are unbounded `TEXT`.
- **Failure:** `hindsightTotal` then returns null while the UI renders an empty `{hindsight}` cell (`s/[token]/page.tsx:88`). Direct writes bypass the API rules.
- **Fix:** Add CHECKs: hindsight scores are all null or all non-null, `outcome IS NOT NULL` when status is not ACTIVE, and length limits. Note that the CHECKs live only in raw SQL and are invisible to `schema.prisma`, so document them.

**10. Unbounded reads, no pagination and no size limits**
- **Where:** `src/app/api/ideas/route.ts:15-21`, `src/app/ideas/page.tsx:12-15`, `src/components/ideas-dashboard.tsx`
- **Problem:** Every idea, with a description up to 5,000 characters, is loaded, sorted in JS and sent to the client. There is no per-user idea cap and no request body size limit.
- **Failure:** An account that creates thousands of ideas (possible given finding 2) makes its dashboard slow and heavy for the server and the browser.
- **Fix:** Paginate, sort in SQL (`orderBy` total via a computed or generated column), cap ideas per user, and limit body size.

## Low

**11. Account enumeration**
- **Where:** `src/app/api/auth/register/route.ts:20-25`, `src/app/api/auth/login/route.ts:19-22`
- **Problem:** Register returns an explicit 409 for an existing email. Login returns immediately for an unknown user but takes about 250 ms of bcrypt for a known one.
- **Failure:** Anyone can test whether an email has an account.
- **Fix:** Run a dummy `bcrypt.compare` for unknown users. Decide whether the 409 is acceptable and rate-limit it.

**12. Password handling**
- **Where:** `src/lib/validation.ts:6`
- **Problem:** `bcrypt` uses only the first 72 bytes, but the limit is 200 characters, so a longer password is silently truncated. I'm not certain whether `bcryptjs` 3.x truncates silently or throws, so **confirm this**. The policy also has no breached-password check.
- **Fix:** Cap at 72 bytes or pre-hash, and consider a breach-list check.

**13. No account lifecycle**
- **Where:** missing throughout
- **Problem:** There is no password reset, email verification, change password, change email, or account and data deletion.
- **Failure:** A forgotten password means a lost account. Anyone can register an email they don't own. There is no way for a user to delete their data, which matters for GDPR.
- **Fix:** Add these flows before launch, or state explicitly that they are out of scope.

**14. Origin and Content-Type not checked on state-changing routes**
- **Where:** all POST, PATCH and DELETE handlers, e.g. `login/route.ts:8`
- **Problem:** Protection rests on `SameSite=Lax` alone. `req.json()` parses regardless of `Content-Type`.
- **Failure:** A cross-site form can log a victim into an attacker-controlled account (login CSRF). Same-site subdomain attackers can also post with the cookie.
- **Fix:** Require `Content-Type: application/json` and verify the `Origin` header.

**15. JWT verification is not pinned**
- **Where:** `src/lib/auth.ts:44`
- **Problem:** `jwtVerify` has no `algorithms`, `issuer` or `audience` option.
- **Fix:** Pass `{ algorithms: ["HS256"], issuer, audience }` and set the same values when signing.

**16. Share links are indexable and never expire**
- **Where:** `src/app/s/[token]/page.tsx:12-22`, `src/app/api/ideas/[id]/share/route.ts`
- **Problem:** There is no `robots: noindex`, no `Cache-Control` and no expiry option. The token is stored in plaintext.
- **Failure:** A link posted publicly can be indexed, and it stays live until manually revoked. A DB leak exposes every live link.
- **Fix:** Add `robots: { index: false }`, an optional expiry, and consider storing a hash of the token.

**17. `serializeIdea` returns the whole row**
- **Where:** `src/lib/serialize-idea.ts:7`
- **Problem:** `...idea` includes `userId`, and any column added later is returned automatically. The public share route uses an explicit allow-list, so the two are inconsistent.
- **Fix:** Use an explicit allow-list here too.

**18. `getCurrentUser` loads `passwordHash` on every request**
- **Where:** `src/lib/session.ts:40`, `src/lib/api-auth.ts:8`
- **Problem:** The layout's `SiteHeader` calls it on every page render, and `requireUser` hands the full `User` row, including the hash, to route code.
- **Failure:** A future `NextResponse.json({ user })` would leak the hash.
- **Fix:** Use `select` to return only `id`, `email` and `name`.

**19. Client error handling**
- **Where:** `src/components/auth-form.tsx:26`, `idea-create-form.tsx:40`, `idea-detail.tsx:57,73`, `share-control.tsx:27,42,51`, `logout-button.tsx:13`
- **Problem:** `fetch` rejections are uncaught. Delete, share and revoke failures are silently ignored, and `clipboard.writeText` isn't guarded.
- **Failure:** A network error leaves the auth form stuck on "Please wait…". A failed revoke looks successful.
- **Fix:** Wrap in try/catch, surface errors, and map Zod messages to user-friendly text (the raw `issues[0].message` is shown, `validation.ts`).

**20. Invalid `status` filter silently ignored**
- **Where:** `src/app/api/ideas/route.ts:13-19`
- **Problem:** `?status=bogus` returns all ideas instead of a 400.
- **Fix:** Return 400 on an invalid value.

**21. `docker-compose.yml` exposes Postgres with default credentials**
- **Where:** `docker-compose.yml:5-10`
- **Problem:** Port 5432 is published on all interfaces with `idealog/idealog`, which match `.env.example`. There is no healthcheck and the image is not pinned to a patch version.
- **Failure:** On a server or shared network, the DB is reachable with a known password.
- **Fix:** Bind `127.0.0.1:5432:5432` and source credentials from env. Add a healthcheck.

**22. Runtime version and dependency hygiene**
- **Where:** `README.md:23`, `package.json` (no `engines`), `@types/node ^20`
- **Problem:** The README says "Node 20+". Node 20 reached end of life in April 2026, so I'd treat it as unsupported now, which is worth confirming. There is no `engines` field or `.nvmrc`. `@prisma/client` is `^6.19.3` while `prisma` is pinned exactly, so they can drift apart.
- **Fix:** Target Node 22 or later, add `engines`, and pin both Prisma packages to the same exact version.

**23. No logging or monitoring**
- **Where:** `src/lib/prisma.ts:10`
- **Problem:** Only Prisma errors are logged. Failed logins, registrations and 5xx responses are not recorded, and there is no error tracking.
- **Fix:** Add structured logging of auth events and an error reporter.

**24. Post-login redirect and accessibility**
- **Where:** `src/proxy.ts:14-16`, `src/components/ideas-dashboard.tsx:75`, `src/components/score-picker.tsx`
- **Problem:** The proxy redirects to `/login` without a return URL, so deep links are lost after login. Tabs are plain buttons with no `role="tab"` or `aria-selected`, the score radiogroup has no arrow-key handling, and error messages have no `role="alert"`.
- **Fix:** Add a validated `next` parameter (same-origin paths only) and fix the ARIA roles.

## Informational

- **Dead public API route:** `src/app/api/share/[token]/route.ts` is not used by any page or component. `/s/[token]` queries Prisma directly and recomputes the delta, so there are two copies of the logic. Remove the route or use it.
- **Duplicate query:** `s/[token]/page.tsx` runs the same `findUnique` twice per request (`generateMetadata` and the page). Wrap it in React `cache`.
- **Every page hits the DB:** `SiteHeader` in the root layout calls `getCurrentUser()` on every page, including the public share page.
- **Redundant index:** `Idea_userId_idx` is redundant with `Idea_userId_status_idx`, whose prefix already covers it.
- **Config duplication:** Build-script allowlists sit in both `package.json` and `pnpm-workspace.yaml`. `sharp` is ignored, which matters only if `next/image` is used later.
- **Leftover assets:** `public/*.svg` are unused create-next-app defaults.
- **README wording:** It says "unshareable/unguessable link", presumably meaning "unguessable". It describes a "cookie session", but the session is a stateless JWT (see finding 6). It has no LICENSE, security or privacy notes, and no data-retention statement.
- **Cookie name:** The session cookie isn't `__Host-` prefixed.
- **Unverified Next 16 conventions:** `src/proxy.ts` uses the `proxy` export and `config.matcher`, `layout.tsx` uses the global `LayoutProps<"/">` type, and `AGENTS.md` warns that this Next version differs from what I know. I could not check either without `node_modules`. Run `pnpm install && pnpm build && pnpm lint` and confirm the proxy actually runs on `/ideas` and `/ideas/:id`.
